**Дисципліна:** Сучасні технології баз даних   
**Варіант 4:** система управління лікарнею  
**Попередня робота:** <https://github.com/zlat1x/hospital-database-lab-variant-4>

## Мета

Вивчити основні типи нереляційних баз даних; оцінити обґрунтованість використання NoSQL у лікарняній інформаційній системі; спроєктувати однакову бізнесову функціональність у PostgreSQL та MongoDB; перевірити коректність запитів і порівняти їхню швидкодію за відтворюваною методикою; реалізувати базові операції в Redis як NoSQL сховищі іншого типу.

## 1. Види NoSQL

| Тип | Модель | Типові звернення | Приклад технології | Обмеження |
| --- | --- | --- | --- | --- |
| **Ключ–значення** | Ключ однозначно адресує значення; можуть бути структури рядків, хешів, множин | `GET key`, `SET key`, TTL | Redis | Пошук за довільними полями значення непрямий; необхідна політика витіснення/стійкості |
| **Документний** | BSON/JSON-подібні документи з вкладеними полями та масивами | читання цілісного документа, фільтри, агрегування | MongoDB | Дублювання, правила валідації, розмір документа, складність кросдокументної цілісності |
| **Широкостовпцевий** | Партиції, упорядковані рядки за clustering columns; схема орієнтується на шлях доступу | дані конкретного ключа розділу за часом | Apache Cassandra | Погано підходить для довільних join і запитів без відомого ключа розділу |
| **Графовий** | Вершини, ребра, властивості; дослідження шляхів та зв'язків | обходи, суміжні сутності, шляхи | Neo4j | Не кожен зв'язок виправдовує графову систему; великі обходи дорогі |

**Висновок:** NoSQL об’єднує різні моделі СУБД і сам по собі не означає вищу швидкодію порівняно з SQL. Вибір залежить від моделі доступу, вимог цілісності, обсягів і витрат підтримки. Підхід відповідає матеріалам лекцій про NoSQL, документні БД, ключ–значення, широкостовпцеві та графові БД.

## 2. Аналіз предметної області, зв'язок із лабою № 1

### Вихідна модель

У першій лабораторній роботі реалізовано таблиці `hospital.patient`, `hospital.appointment`, `hospital.encounter`, `hospital.lab_test`, `hospital.lab_order`, `hospital.lab_order_item` (а також інші сутності), PostgreSQL 16, перевірки цілісності, soft delete, тригери й аудит. `lab_order_item.result_text` зберігає довільний текст результату; базова модель не призначена для великої варіативної історії числових показників із референтними межами в різних панелях.

### Додана вимога до уявного застосунку

Лікарня інтегрує результати діагностичних пристроїв/лабораторій. Один лабораторний звіт містить **обмежений набір панелей** (тут CBC і MET), кожна панель містить різні показники. Потрібні:

1. Швидко відкрити **весь звіт** за ID (разом із вкладеними показниками).
2. Повернути **10 останніх ID звітів** конкретного пацієнта.
3. Обчислити **кількість значень поза референтним діапазоном** в історії пацієнта.
4. Отримати **20 останніх вимірів обраного маркера** (GLU) конкретного пацієнта.
5. Виправити **один показник** звіту за унікальним шляхом.
6. Створити новий **цілісний звіт** із двома панелями, вісьмома значеннями.

Розширення вимог до предметної області реалізовано у відокремленому експериментальному модулі без змін основної бази лабораторної роботи № 1. У цьому проєкті ідентифікатори `DEMO-P.....` синтетичні, `source_encounter_id` дорівнює `NULL`. Жодні справжні лікарняні дані не використовуються.

### Чому MongoDB може бути доцільною

Коли користувач відкриває звіт, зазвичай потрібні і заголовок, і кілька пов'язаних панелей, і їхні результати. Цей **обмежений агрегат** може зберігатися одним документом; його зручно передати в інтерфейс, змінювати структуру нових типів панелей, атомарно оновлювати вміст **одного** документа. MongoDB підтримує індекси за пацієнтом/часом, вкладені масиви, агрегації та валідацію.

**Межі застосування:** ключові відомості про пацієнтів, госпіталізації, призначення, права й аудит мають складні зв'язки, транзакційні інваріанти і повинні залишатись у PostgreSQL. Запити по всіх вимірюваннях, агрегації в історії та зміни довідників у MongoDB можуть коштувати дорожче. MongoDB — кандидат для конкретного контуру звітів, а не доведена заміна основної БД.

### Узгодженість кількох СУБД

У реальній системі визначають **одне авторитетне джерело для кожного факту**, стабільний `source_lab_order_id`, правила доставки/повторів, подію з унікальним ID та контроль версій. Для сценарію з копією у MongoDB потрібен outbox/черга, ідемпотентний імпорт, журнал помилок, повторення, звіряння кількості/хешів. Суміжні зміни PostgreSQL + MongoDB **не стають атомарною транзакцією автоматично**. Медичні та персональні дані вимагають окремих правил безпеки й доступу; тут лише демонстраційні дані.

## 3. Реалізація у MongoDB

Колекція `hospital_lab2.reports`. Один BSON-документ — один лабораторний звіт:

```javascript
{
  _id: "R00000001",
  patient_id: "DEMO-P00001",
  source_encounter_id: null,
  collected_at: ISODate("2026-01-01T00:07:00Z"),
  status: "final",
  panels: [
    { code: "CBC", measurements: [
      { code: "WBC", label: "White blood cells", unit: "10^9/L",
        value: 9.10, reference_low: 4.0, reference_high: 10.0 },
      /* ще три вимірювання панелі CBC */
    ] },
    { code: "MET", measurements: [
      { code: "GLU", label: "Glucose", unit: "mmol/L",
        value: 5.0, reference_low: 3.9, reference_high: 6.1 },
      /* ще три вимірювання панелі MET */
    ] }
  ]
}
```

*Наведений JSON є поясненням структури, не дослівним значенням запису генератора; точні детерміновані числа створює `src/dataset.py`.*

- `_id` — стабільний ID звіту; `patient_id` — ID синтетичного пацієнта, не ПІБ.
- `panels` — не безмежна історія: максимум 5 панелей, максимум 32 вимірювання в панелі відповідно до JSON Schema-валідації колекції.
- `reference_low`/`reference_high` — історичні межі **саме цього звіту**. Перегляд старого результату не повинен залежати від того, що довідник оновлено згодом.
- `label` і `unit` дублюються всередині звіту для повного читання; це **історичні знімки**, а не актуальний глобальний довідник.
- Індекси: `ix_patient_time` (`patient_id`, `collected_at DESC`, `_id DESC`), `ix_patient_marker_time` (`patient_id`, `panels.measurements.code`, `collected_at DESC`), стандартний `_id`.

**Операції:** `find_one`, `find().sort().limit()`, агрегування `$match/$unwind/$count`, `$sort/$limit`, `update_one` з `array_filters`, `insert_one`. Готові запити: `mongo/queries.js` і Python-реалізації `src/stores.py`.

## 4. Еквівалентна SQL-модель

**PostgreSQL 16**, окрема схема `lab2` (схема `hospital.*` з першої роботи залишається незмінною):

```text
lab2.report
  id PK, patient_id, source_encounter_id NULL,
  collected_at, status
    │ 1:N
    ▼
lab2.panel
  (report_id, code) PK; report_id FK → report.id
    │ 1:N
    ▼
lab2.measurement
  (report_id, panel_code, test_code) PK
  (report_id, panel_code) FK → panel PK
  (panel_code, test_code) FK → test_catalog PK
  value_num, reference_low, reference_high
    │ N:1
    ▼
lab2.test_catalog
  (panel_code, test_code) PK, display_name, unit
```

Таблиця `test_catalog` нормалізує **назви та одиниці** тестів; вимірювання зберігають числове значення й історичні межі. Назви в SQL отримують через join, тоді як MongoDB вкладає їх безпосередньо в документ. Це відображення **одного MongoDB-документа у декілька SQL-таблиць**, як вимагає пункт 5. Важлива різниця: якщо глобальна назва/одиниця в `test_catalog` зміниться, SQL-подання старих записів зміниться, тоді як MongoDB зберігає знімок. У нашому навчальному наборі довідник **незмінний**; для виробничої історичної точності SQL-модель варто розширити версіонованим довідником або знімками назви/одиниці. Це обмеження явно зафіксоване, а не приховане.

Визначення PK, FK, CHECK та індексів наведено в `db/schema.sql`; ER-діаграму подано у форматі `schema/lab2.dbml`; приклади запитів Q1–Q5 містяться в `db/queries.sql`. Відповідність вимогам не базується на порівнянні кількості таблиць: порівнюємо **семантично однакові бізнес-операції та обсяг корисних даних**.

## 5. Протокол вимірювання швидкодії

### Дані та масштаби

- Відтворюваний генератор `src/dataset.py`; фіксована формула для чисел і часу, без реальних ПІБ та медичних висновків.
- Однакові ID, пацієнти, моменти, маркери та значення в обох базах. Один звіт має 2 панелі × 4 показники = 8 вимірів.
- Рекомендовані набори: **1 000 звітів / 8 000 вимірювань**, **10 000 / 80 000**, **50 000 / 400 000**. Розмір найбільшого набору залежить від ресурсів ноутбука.
- Історія кожного пацієнта містить багато звітів, а розкид числових значень створює і нормальні, і аномальні випадки.

### Контроль коректності (обов'язково до часу)

`src.validate` перевіряє однакову кількість документів/звітів, кількість показників, 50 (або більше) **повних звітів** після відновлення SQL із 4 таблиць і всі 4 читальні сценарії для 12 пацієнтів. `--all` перевіряє **кожний** звіт. Якщо дані різні, сценарій **не можна** вважати еквівалентним; бенчмарк зупиняється.

### Порівнювані сценарії

| Сценарій | SQL | MongoDB | Результат та обґрунтування |
| --- | --- | --- | --- |
| **Q1** Повний звіт | JOIN 4 таблиць та складання 1 об'єкта | `find_one` за `_id` | Однаковий цілісний звіт із панелями/значеннями; основний use case для MongoDB |
| **Q2** Останні 10 ID | Індексовані `WHERE + ORDER BY + LIMIT` | Композитний індекс, проєкція лише `_id` | Порівнюємо **лише 10 ID** у двох базах, а не документ проти ID |
| **Q3** Аномальні результати | JOIN + порівняння `value_num` з межами | `$match` пацієнта, два `$unwind`, `$expr`, `$count` | Однакова кількість відхилень; може бути дорого для вкладеної структури |
| **Q4** Останні 20 GLU | JOIN, умова за кодом, `ORDER BY`, `LIMIT` | `$match`, `$unwind`, `$sort`, `$limit` | Однакові трійки (report ID, час, value) |
| **W1** Зміна WBC | UPDATE одного рядка в транзакції | `update_one` із двома `arrayFilters` | Змінюємо **один** вимір, не весь звіт; початкове значення відновлюється |
| **W2** Створення звіту | Одна транзакція: report + 2 panel + 8 measurement | Один `insert_one` документа | Однакова логічна одиниця, різна кількість фізичних вставок; потім очищення |

### Гіпотези та критерій оцінки

- **Гіпотеза H1:** MongoDB може зменшити затримку читання цілого звіту (Q1) та вставки цілого агрегату (W2), бо ці дані є одним документом; це **не припущення про гарантовану перемогу**.
- **Гіпотеза H2:** SQL може бути конкурентнішим для обчислення відхилень та історії окремого показника (Q3, Q4), бо результати зберігаються окремими індексованими рядками.
- **Практичний критерій:** як навчальний поріг для *помітної* різниці на конкретному сценарії використовуємо відхилення p50 понад **20%** з однаковим напрямком на наборах 10 000 і 50 000. Це умовний критерій інтерпретації, **не статистичний доказ**, не універсальний SLA і не заміна оцінки p95, ресурсів та витрат підтримки. Якщо спостереження неоднозначні, гіпотеза залишається непідтвердженою.

### Методика

1. SQL/MongoDB/Redis у різних локальних Docker-контейнерах, одна машина, доступ через `localhost` TCP. Порти фіксовані; параметри сервера й ОС записуються у JSON.
2. Обидві БД мають індекси під реальні фільтри; SQL `ANALYZE` після завантаження. Плани читальних сценаріїв збираються поза таймером в `*_plans.json`: SQL `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` та MongoDB `explain` з `executionStats` (де підтримується). Це серверні виміри для діагностики, не основна метрика клієнтського round trip.
3. Кожну операцію прогрівають, потім виконують багаторазово з різними ID/пацієнтами (детермінована вибірка `Random(20261110)`). Порядок запуску SQL/MongoDB **чергується** для зменшення систематичного впливу черги.
4. Вимірюємо `time.perf_counter_ns()` **навколо повного клієнтського виклику**: мережа localhost + рушій + читання/складання відповіді; без часу генерації та початкового завантаження. Один клієнт; серійне виконання, не throughput конкурентної системи.
5. Додатково зберігаємо обсяг PostgreSQL-таблиць з індексами та доступні MongoDB storage/index метрики; формати не повністю зіставні, але показують ціну денормалізації. Зберігаємо **n, середнє, мінімум, максимум, p50, p95**, оцінюємо операції/с у серійному режимі (`1000/mean_ms`). Не порівнюємо лише один мінімальний час.
6. Після W1 відновлюємо оригінальний результат, після W2 видаляємо тільки тимчасові `TMP-BENCH-...` записи, і **знову перевіряємо** коректність.
7. Три масштаби запускати окремо і зіставляти тренд: час на 1 000 записів може мало що сказати про 50 000 і навпаки.

### Обмеження експерименту

- Не вимірює холодний диск/кеш, навантаження кількох одночасних клієнтів, горизонтальне масштабування, реплікацію й відмовостійкість.
- Не порівнює із PostgreSQL JSONB/матеріалізованими проєкціями: це ще один законний варіант без нового продукту.
- Не робить рівними гарантії довговічності: локальні конфігурації за замовчуванням можуть відрізнятися, а `insert_one` одного документа проти транзакції з трьома SQL-таблицями відображає **реальну ціну обраної моделі**, але не абстрактну «швидкість рушія».
- Не дозволяє сказати «MongoDB завжди швидша». Q1 та W2 можуть сприяти документу; Q3 та Q4 можуть сприяти SQL, і **це треба перевірити**.
- Не відтворює клінічних даних, не придатний для медичного прийняття рішень.

### Результати

Числові результати формуються програмою `src.benchmark` після виконання вимірювань. Для кожного обсягу даних зберігаються CSV, JSON і плани запитів. `src.summarize` формує підсумкові таблиці p50/p95 з отриманого JSON. Підсумковий висновок щодо швидкодії базується на цих результатах; до виконання запусків наведена лише методика експерименту.

## 6. Друга NoSQL база іншого типу — Redis

**Модель:** ключ–значення, на відміну від документної MongoDB. **Роль:** кеш відновлюваних коротких підсумків лабораторних звітів; не єдине сховище історичних результатів.

Приклад ключового простору: `hospital-lab2:demo:latest:DEMO-P00001`.

| Операція | Демонстрація | Що ілюструє |
| --- | --- | --- |
| `SET key value EX 120` | JSON-підсумок останнього звіту | прямий доступ + TTL |
| `GET key`, `TTL key` | читання й залишок строку життя | cache hit та строк чинності |
| `HSET`, `HGETALL`, `HGET` | метадані звіту як hash | робота з полями без повної заміни JSON |
| `SADD`, `SMEMBERS`, `SISMEMBER`, `SCARD` | множина кодів аналізів | унікальність і перевірка належності |
| `EXPIRE` | TTL для hash/set | обмежене зберігання |
| `DEL` | очищення лише демо-ключів | видалення з визначеного простору |

Код: `src/redis_demo.py`. Ключі не містять ПІБ; використано демонстраційний префікс, автоматичне очищення й перевірки результатів. Для кешу потрібен сценарій відновлення з PostgreSQL/MongoDB; TTL та eviction не гарантують, що ключ існуватиме весь запланований строк.

## Підсумковий висновок

Архітектурно виправданий варіант — **залишити основні зв'язані дані лікарні у PostgreSQL**, а обмежені багатоскладові звіти розглядати як кандидата для MongoDB, якщо типовий запит відкриває весь агрегат. Redis доречний як TTL-кеш для відновлюваних зведень. Рішення про винесення даних **не можна ухвалювати лише за кількістю JOIN чи назвою NoSQL**: необхідно перевірити профіль реальних запитів, цілісність, безпеку та вартість синхронізації. Власні бенчмарки розрізняють сценарії, в яких кожна модель ефективна, та демонструють межі порівняння.
